## MUST_FIX 验证

### MUST_FIX-1: Post-Dispatch Verification 缺少修复流程

**v1 问题：** 声明了"验证失败必须修复"但没有定义修复路径，可能导致无限重试、跳过验证、修错文件。

**验证结果：已修复。**

文件中新增了完整的修复流程：

1. **失败类型处理表格**：4 种失败类型（文件不存在、编译失败、新增测试失败、已有回归）各有对应处理方式，dispatch fix subagent 并传入不同上下文（缺失文件列表 / 编译错误输出 / 回归标注）。
2. **重试上限**：最多 2 轮重试，防止无限循环。
3. **降级路径**：2 轮后仍失败 → 标记 BLOCKED，记录 memory.md，跳过当前 task 继续。
4. **职责边界消歧**：新增"与 Handling Implementer Status 的区别"段落，明确两个检查点的不同职责和处理路径，消除 v1 额外发现 2 的歧义。

### MUST_FIX-2: Pre-Dispatch 禁止派遣缺少重试路径

**v1 问题：** 禁止派遣但没有说明补充信息的具体流程——从哪里获取、grep 失败怎么办。

**验证结果：已修复。**

Pre-Dispatch Checklist 后新增"信息缺失时的补全顺序"：

1. `grep` 代码提取 → 优先（最可靠）
2. 读 spec/plan 文档 → 次选（可能有偏差）
3. 标记 `[UNVERIFIED]` 并声明 → 最后手段（仅限枚举值/import 路径，方法签名缺失必须回 Step 1）

三步递进，有明确的适用范围和边界，不会导致主 agent 行为不一致。

### MUST_FIX-3: 并行依赖安全检查边界情况

**v1 问题：** 循环依赖、间接依赖、编译时依赖三种边界情况未覆盖。

**验证结果：已修复。**

Wave 模式章节新增三条注意事项：

1. **循环依赖（A↔B）**：标记为 plan 缺陷，BLOCKED 并报告用户，不自行拆分。
2. **间接依赖**：明确只检查直接接口引用，不追踪间接依赖（A→B→C 中 A 和 C 的间接关系），避免过度分析。
3. **编译时依赖**：共享类型文件 import 不算接口依赖，允许并行，防止误报。
